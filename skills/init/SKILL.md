# Guided initialization

Step ids: `cli, login, connection, write-config, update-gitignore, commit, discovery, guards`

## 0. Follow the safety rules

Never paste or accept an API key in chat. Never run a step the user has not approved. `shore-guard <command> --help` is safe to run. If `shore-guard` is not on PATH, use `node "${CLAUDE_PLUGIN_ROOT}/bin/shore-guard"` for every command below. If the CLI is missing entirely, ask the user to run `npx shore-guard setup` in a terminal, or `npm install -g shore-guard`.

Apply the completion-contract exit-code table to every CLI result: 0 continue; 1 remediate findings; 2 repair configuration or the internal error; 3 log in or escalate; 4 remediate remote availability; 5 remediate quota; 6 follow decision and git-safety guidance; 7 commit or restore a clean tree. For any other exit, escalate. Stop on every nonzero exit after giving its remediation.

Manual:
`shore-guard <command> --help`

## 1. Read the plan

Run `shore-guard init --plan --json`. Parse `data.plan`. If the exit is nonzero, apply the completion-contract table and stop with the remediation.

Manual:
`shore-guard init --plan --json`

## 2. Ask for one approval

Present `data.plan.steps` as a numbered list. Show a status marker, `title — detail`, every `changes` path when present, and the `manual` command. Then ask exactly one question with exactly these options:

(a) Do all remaining steps on a new worktree branch `shore-guard/setup` (recommended)

(b) Do them on the current branch

(c) I'll do it myself — print the full runbook (`RUNBOOK.md`) and stop

Do not proceed without an explicit choice. For (c), print the complete adjacent `RUNBOOK.md` and stop.

Manual:
Choose (a), (b), or (c).

## 3. Complete login

If `login` is pending or blocked, ask the user to run `shore-guard login` in their own terminal. Wait, then rerun the plan. Browser login is coming in SCRUM-103; until then login stays in the user's terminal. Never ask them to paste a key into chat.

Manual:
`shore-guard login && shore-guard init --plan --json`

## 4. Confirm the connection

If `connection` is blocked, relay its `reason`, tell the user to connect the repository in Shore Sight, and stop. Continue only after a rerun reports that the connection passes.

Manual:
Connect the repository in Shore Sight, then run `shore-guard init --plan --json`.

## 5. Prepare the approved branch

For (a), work from the repository root. Detect the default branch with `git symbolic-ref refs/remotes/origin/HEAD`, stripping `refs/remotes/origin/`; fall back to `main`. Run `git worktree add ../.worktrees/shore-guard-setup -b shore-guard/setup <default-branch>`, then run every remaining command inside that worktree. For (b), require empty output from `git status --porcelain`; otherwise stop.

Manual:
`git symbolic-ref refs/remotes/origin/HEAD` then `git worktree add ../.worktrees/shore-guard-setup -b shore-guard/setup <default-branch>`, or `git status --porcelain`.

## 6. Initialize

Run `shore-guard init --json`, not `--plan`. Apply the completion-contract exit-code table and stop with its remediation on any nonzero exit.

Manual:
`shore-guard init --json`

## 7. Review and commit

Show `git status --porcelain`, `git diff -- .gitignore`, and the full `.shore/guard.json`. Ask the user to approve the commit. Only after approval, stage `.shore/guard.json` and `.gitignore`, then commit with `chore: add Shore Guard configuration`.

Manual:
`git add .shore/guard.json .gitignore && git commit -m "chore: add Shore Guard configuration"`

## 8. Publish the worktree branch

For (a), run `git push -u origin shore-guard/setup`. If `gh auth status` succeeds, run `gh pr create --base <default> --title "Add Shore Guard configuration" --body <short-body>`; the body must list `.shore/guard.json` and `.gitignore` and say it was generated by `/shore-guard:init`. Otherwise derive `<owner>/<repo>` from `git remote get-url origin`, print `https://github.com/<owner>/<repo>/compare/<default>...shore-guard/setup?expand=1`, and print the manual `gh pr create` command. For (b), do not create a PR; say the commit is on the current branch.

Manual:
`git push -u origin shore-guard/setup && gh pr create --base <default> --title "Add Shore Guard configuration" --body <short-body>`

## 10. Discover architecture policy

After the configuration commit, follow the discovery skill; do not reinvent it here. Write the proposal to `.shore/proposals/<YYYY-MM-DD>-discovery.json`, then summarize its modules, edges, rules, and tradeoffs in no more than 10 lines. Ask exactly one question with exactly these options: approve / modify / reject / skip. When adopt succeeds, follow the guards skill for the final guards step.

For approve, run `shore-guard adopt --proposal <file> --approve --json`. For modify, ask the user to edit the proposal JSON, then rerun adopt with `--approve`. For reject, run `shore-guard adopt --proposal <file> --reject --json`; rejection writes nothing. For skip, say discovery can be run later from the discovery skill and continue to finish.

After approval, show `git status --porcelain` and the diffs for `.shore/policy.json`, `.shore/policy.lock.json`, and `AGENTS.md`. Ask for approval, then commit them with `chore: adopt Shore Guard architecture policy`. For option (a), push to the same `shore-guard/setup` branch so the pull request includes the policy; if the pull request already exists, say the push updates it.

Manual:
`shore-guard adopt --proposal <file> --approve --json`

## 11. Finish

Run `shore-guard doctor --json` and summarize the result using the completion-contract table. Remind the user that `check` and `verify` need the configuration commit on the branch being verified.

Manual:
`shore-guard doctor --json`
